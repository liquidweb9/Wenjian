## Implementation Summary

### 1. Question Form Types (`app/interview/question_forms.py`)

**Purpose**: Define 8 distinct question forms that test different aspects of ability.

**Question Forms**:
- **CONCEPT** (理论理解) - Tests theoretical understanding, principles, definitions
- **DESIGN_RATIONALE** (设计决策) - Tests architectural thinking and decision-making
- **PROJECT_DETAIL** (实现细节) - Tests implementation depth, code structure, data flow
- **DEBUGGING** (问题诊断) - Tests problem diagnosis and troubleshooting ability
- **PRODUCTION_SCENARIO** (生产环境) - Tests production awareness, monitoring, operations
- **TRADE_OFF** (权衡分析) - Tests tradeoff analysis, cost vs. benefit thinking
- **COUNTERFACTUAL** (反事实) - Tests transfer ability under changed constraints
- **EVOLUTION** (演进思维) - Tests system evolution and scaling thinking

### 2. QuestionFormSelector (`app/interview/question_forms.py`)

**Purpose**: Select appropriate question forms based on depth, avoiding repetition.

**Key Features**:
- Depth-aware selection (shallow depths prefer CONCEPT, deep depths prefer COUNTERFACTUAL)
- Repetition avoidance (tracks form history per competency)
- Project context filtering (forms requiring project details only when available)
- Coverage tracking (identifies untested abilities)

**API**:
```python
selector = QuestionFormSelector()

form = selector.select_form(
    competency_code="backend.api_design",
    current_depth=3,
    project_context_available=True,
    form_history=["concept", "project_detail"],
)
# Returns: QuestionForm.DEBUGGING (avoids already-used forms)

coverage = selector.get_form_coverage(form_history)
# Returns: {"concept": 1, "project_detail": 1, "debugging": 0, ...}

untested = selector.get_untested_abilities(form_history)
# Returns: ["problem_solving", "transfer_ability", ...]
```

**Selection Logic**:
1. Filter forms by depth range (e.g., COUNTERFACTUAL only for depth 6-7)
2. Filter forms requiring project context
3. Exclude forms already used (from form_history)
4. Prioritize forms matching current depth best
5. If all forms used, allow repetition but prefer less-used forms

### 3. CounterfactualGenerator (`app/interview/counterfactual.py`)

**Purpose**: Generate "what if" questions that change project constraints to test adaptability.

**Constraint Change Types**:
- **Scale** (规模变化): 10x or 100x increase in QPS/users/data
- **Dependency** (依赖故障): Database down, cache unavailable, network partition
- **Cost** (成本约束): Reduce operational cost by 50%
- **Timeline** (时间压力): Deliver in 1/3 of original time
- **Team** (团队规模): Only 2 engineers instead of full team
- **Requirement** (需求扩展): New use case (real-time, multi-tenancy, internationalization)

**API**:
```python
generator = CounterfactualGenerator()

scenarios = generator.generate_constraint_changes(
    project_context={
        "title": "分布式任务调度系统",
        "tech_stack": ["Redis", "RabbitMQ", "PostgreSQL"],
    },
    verified_facts=[
        "系统处理QPS约1000",
        "使用Redis作为缓存",
    ],
)
# Returns: List of 6 scenario dicts with change_type, description, constraints

question = generator.build_counterfactual_question(
    scenario=scenarios[0],
    project_name="任务调度系统",
    depth=7,
)
# Returns: Formatted Chinese question with project context
```

**Scenario Binding**:
- Extracts scale info from verified facts (QPS, users, data volume)
- References actual tech stack for dependency failures
- Uses project timeline/team size when available
- All scenarios grounded in project reality, not generic

## Architecture Patterns

### 1. Form-Depth Mapping

Different forms are suited for different depth levels:

| Depth | Preferred Forms | Focus |
|-------|----------------|-------|
| 1-2 | CONCEPT, PROJECT_DETAIL | Background, execution flow |
| 3-4 | PROJECT_DETAIL, DESIGN_RATIONALE, DEBUGGING | Implementation, design decisions |
| 5-6 | TRADE_OFF, PRODUCTION_SCENARIO, DESIGN_RATIONALE | Production, tradeoffs, architecture |
| 7 | COUNTERFACTUAL, EVOLUTION | Transfer ability, system evolution |

### 2. Repetition Avoidance

```python
# First question on Redis caching (depth 2)
form1 = selector.select_form(..., form_history=[])
# Returns: PROJECT_DETAIL

# Second question on same competency (depth 3)
form2 = selector.select_form(..., form_history=["project_detail"])
# Returns: DEBUGGING (avoids PROJECT_DETAIL)

# Third question (depth 4)
form3 = selector.select_form(..., form_history=["project_detail", "debugging"])
# Returns: DESIGN_RATIONALE
```

### 3. Counterfactual Binding

Counterfactual questions are grounded in verified project facts:

```python
# User answered: "系统QPS为5000, 使用Redis缓存"
# Status: VERIFIED

# Counterfactual generates:
"假设「分布式缓存系统」需要在以下约束下重新设计：如果QPS从5000增加到50万。

如果QPS增加到50万倍，你的方案中哪些部分会成为瓶颈？你会如何调整架构？

请详细说明你会如何调整架构、技术选型、实现方案，以及这样调整的理由。"
```

## Known Limitations

### 1. Form Selection Heuristics

**Current**: Rule-based form selection based on depth ranges  
**Limitation**: No learning from user performance  
**Future**: Use historical answer quality to bias form selection (e.g., if user weak on debugging, prioritize DEBUGGING forms)

### 2. Counterfactual Scenario Simplicity

**Current**: 6 fixed scenario types (scale, dependency, cost, timeline, team, requirement)  
**Limitation**: Scenarios not customized to specific project domain  
**Future**: Domain-aware scenarios (e.g., ML projects get "data distribution shift" scenarios)

### 3. No Semantic Duplicate Detection

**Current**: Form diversity reduces repetition, but doesn't prevent semantically similar questions  
**Limitation**: Two PROJECT_DETAIL questions might still overlap  
**Future**: Embedding-based duplicate detection across forms

### 4. Form Coverage Not in Report

**Current**: Form history tracked but not displayed to user  
**Limitation**: User can't see which abilities were tested  
**Future**: Add form coverage visualization to interview report
