## Overview

Implemented production-ready user authentication and authorization system with JWT tokens, password hashing, and object-level permission enforcement.

## Implementation Summary

### 1. User Model (models.py)
- **Table**: `users` with email, hashed_password, full_name, is_active, is_verified
- **Indexes**: Unique index on email for fast lookups
- **Timestamps**: created_at, updated_at, last_login_at
- **Foreign Keys**: Added user_id to resume_sources, interviews, job_targets, ability_observations, ability_profiles, training_tasks

### 2. Security Module (core/security.py)
**Password Hashing**:
- Uses bcrypt via passlib for secure password storage
- Automatic salt generation (different hash each time)
- Functions: `hash_password()`, `verify_password()`

**JWT Token Management**:
- HS256 algorithm with configurable secret key
- 30-day default expiration (configurable)
- Functions: `create_access_token()`, `decode_access_token()`
- Payload format: `{"sub": user_id, "exp": timestamp}`

### 3. Authentication Dependencies (core/deps.py)
**Dependency injection for FastAPI routes**:
- `get_current_user_id()` - Extracts user_id from Bearer token
- `get_current_user()` - Fetches User model from database
- `get_optional_user_id()` - For endpoints that work with/without auth
- **HTTPBearer** security scheme for automatic token extraction

### 4. Auth Endpoints (api/v1/auth.py)
**POST /api/v1/register**:
- Input: email (EmailStr), password, full_name (optional)
- Creates user with hashed password
- Returns JWT access token immediately
- Validates: email uniqueness, email format

**POST /api/v1/login**:
- Input: email, password
- Verifies password against hash
- Updates last_login_at timestamp
- Returns JWT access token
- Returns 401 for invalid credentials or inactive account

**GET /api/v1/me**:
- Requires: Valid JWT token in Authorization header
- Returns: User profile (user_id, email, full_name, is_active, is_verified, timestamps)
- Returns 401 if token missing/invalid/expired

### 5. Repository Permission Enforcement (persistence/repositories/user_repo.py)
**UserRepository**:
- `get_by_id(user_id)` - Fetch user by ID
- `get_by_email(email)` - Fetch user by email (for login)
- `create(user)` - Create new user
- `update_last_login(user_id)` - Update login timestamp

**ResumeRepository** (auth-enabled):
- `get_by_id(resume_id, user_id)` - **Enforces ownership**: returns None if user doesn't own
- `list_by_user(user_id)` - Only returns user's resumes
- `delete(resume_id, user_id)` - Only deletes if user owns

**InterviewRepository** (auth-enabled):
- `get_by_id(interview_id, user_id)` - **Enforces ownership**
- `list_by_user(user_id)` - Only returns user's interviews
- `delete(interview_id, user_id)` - Only deletes if user owns

**Other Repositories**:
- ReportRepository, JobTargetRepository, AbilityProfileRepository, TrainingTaskRepository
- All enforce user_id checks for data access

## Security Features

### Password Security
✅ Bcrypt hashing with automatic salt  
✅ No plaintext passwords stored  
✅ Resistant to rainbow table attacks  
✅ Configurable work factor (currently 12 rounds)

### Token Security
✅ JWT tokens with expiration  
✅ HS256 signing algorithm  
✅ Tokens include expiration timestamp  
✅ Invalid/expired tokens rejected  
✅ No session storage required (stateless)

### Authorization
✅ Object-level permission checks at repository layer  
✅ User can only access own data (horizontal privilege escalation prevented)  
✅ Foreign key constraints enforce data integrity  
✅ Nullable user_id for backward compatibility (can be made NOT NULL later)

### API Security
✅ HTTPBearer security scheme  
✅ Automatic token extraction from Authorization header  
✅ 401 Unauthorized for missing/invalid tokens  
✅ 403 Forbidden for inactive accounts  
✅ Email validation via pydantic EmailStr

## Known Limitations

1. **Backward Compatibility**: Existing data has NULL user_id. Production deployment requires:
   - Create default "system" user account
   - Backfill existing records with default user_id
   - Make user_id NOT NULL in subsequent migration

2. **Email Verification**: is_verified field exists but no email verification flow implemented

3. **Password Reset**: No password reset/forgot password functionality

4. **Rate Limiting**: No rate limiting on login attempts (vulnerable to brute force)

5. **Token Refresh**: No refresh token mechanism (users must re-login after 30 days)

6. **Multi-factor Authentication**: No 2FA support

7. **OAuth/Social Login**: Only email/password authentication supported
