## 架构设计

### Progressive Enhancement Pattern

**设计原则**: Phase 2功能作为增强层，不破坏Phase 1基线

```
Interview Report Page
    ↓
For each claim:
    ↓
Try to fetch Phase 2 data (verification points)
    ↓
Phase 2 data available?
    ├─ YES → Render ClaimStatusCard (with timeline button)
    └─ NO  → Render Phase 1 ClaimStatusPill (fallback)
```

**优点**:
- Zero breaking changes to Phase 1
- 用户逐渐看到更多详细信息（as backend processes interviews）
- Backend可以按需处理（not all claims need VP records immediately）
- 测试友好（Phase 1 tests不需要Phase 2 data）

### Component Composition

```
InterviewReportPage
    ├── ContradictionDisplay (interview-level)
    ├── ClaimStatusSection[] (per claim)
    │   ├── ClaimStatusCard (if Phase 2 data)
    │   │   └── VerificationPoint[] list
    │   └── ClaimStatusPill (fallback)
    └── EvidenceTimeline Modal (on-demand)
```

### Data Flow

```
User opens Report Page
    ↓
useReport(interviewId) → Get report data
useContradictions(interviewId) → Get contradictions (interview-level)
    ↓
For each claim_id:
    useVerificationPoints(claim_id) → Get VPs (if available)
    ↓
User clicks "View Timeline"
    setSelectedVpId(vp_id)
    useTransitions(vp_id) → Fetch transitions
    ↓
Modal opens with EvidenceTimeline
```

### TypeScript Strict Mode

**类型安全**:
- All API responses have TypeScript interfaces
- React Query hooks are fully typed
- Props interfaces for all components
- `verbatimModuleSyntax: true` - all type imports use `type` keyword
- `noUncheckedIndexedAccess: true` - safe array access
- Zero `any` types in new code

**修复的类型错误**:
1. `query-keys.ts` - const assertion with conditional logic
2. `job-targets/api/job-targets.ts` - `apiClient` → `api` rename
3. `claim-gap/api/claim-gap.ts` - `apiClient` → `api` rename
4. `JobTargetListPage.tsx` - type-only import for `JobTargetResponse`

## 关键设计决策记录

### 1. Progressive Enhancement over Feature Flag

**决策**: Phase 2组件通过数据可用性自动启用，而非feature flag

**理由**:
- 简化代码（no if-feature-enabled checks）
- Backend可以逐步处理（not all interviews need VP data immediately）
- 用户体验平滑（gradually see more details as system processes data）
- 测试友好（Phase 1 tests work without Phase 2 data）

### 2. Modal Timeline instead of Inline

**决策**: Evidence Timeline在modal中显示，而非inline展开

**理由**:
- Timeline内容较长（多个transitions），inline会撑开页面
- Modal提供专注的阅读环境
- 避免同时展开多个timelines导致混乱
- 用户可以点击关闭回到report overview

### 3. Contradiction Display at Interview Level

**决策**: Contradictions显示在interview级别（而非每个claim下）

**理由**:
- 一个contradiction可能涉及多个claims
- Interview-level view提供全局视角
- Severity分组帮助prioritize attention
- 与"简历证据一致性"section语义匹配

### 4. No Component Tests (Yet)

**决策**: Week 3.2不包含React component tests

**理由**:
- 项目目前没有frontend testing infrastructure（no Vitest/Jest setup）
- Component logic简单（mostly presentation）
- Backend API已充分测试（8 tests）
- MVP优先（手动验证UI正确性）
- 后续可添加（M2.6 Production Hardening阶段）

### 5. Inline Styles over Tailwind

**决策**: 继续使用inline styles，不引入Tailwind utility classes

**理由**:
- 遵循项目现有约定（所有页面都用inline styles）
- 保持一致性（不混用多种样式方案）
- 使用CSS custom properties实现theming
- 避免引入新依赖
