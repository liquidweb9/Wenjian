## 架构亮点

### 1. 不可绕过的Guard条件

```python
# VERIFIED状态必须满足3个条件
guard=lambda ctx: (
    ctx.has_evidence_spans and      # 必须有evidence spans
    ctx.strength >= 0.7 and          # 强度阈值
    ctx.confidence in ("MEDIUM", "HIGH")  # 置信度要求
)
```

LLM无法直接将状态设为VERIFIED，必须通过提取evidence spans并满足强度要求。

### 2. 矛盾处理流程

```
发现矛盾
  ↓
CONTRADICTORY (标记矛盾)
  ↓
NEEDS_CLARIFICATION (生成澄清问题)
  ↓
用户回答
  ↓
PARTIALLY_SUPPORTED 或 VERIFIED (根据澄清结果)
```

### 3. 状态可回退

- VERIFIED可回退到CONTRADICTORY（发现新矛盾）
- NEEDS_CLARIFICATION可前进到VERIFIED（澄清后证据充分）
- 支持证据演化的完整生命周期

## 设计决策记录

### 1. State Machine vs Direct LLM Output

**决策**: 使用State Machine + Guard条件，不直接采用LLM输出

**理由**:
- LLM可能hallucinate状态
- Guard条件确保业务规则强制执行
- VERIFIED状态必须有concrete evidence spans
- 可审计、可追溯

### 2. Transition Tracking

**决策**: 记录每次状态转换到`evidence_transitions`表

**理由**:
- 完整的审计跟踪
- 可回溯证据演化过程
- 支持报告生成（Claim → Question → Answer → Transition）
- Prompt/Policy版本控制

### 3. Contradiction流程

**决策**: CONTRADICTORY → NEEDS_CLARIFICATION → 解决

**理由**:
- 不直接判定"候选人撒谎"
- 给候选人澄清机会
- 矛盾可能是误解或上下文不同
- 人性化处理

### 4. Evidence Spans强制

**决策**: VERIFIED状态必须有evidence spans

**理由**:
- 可定位到具体回答文本
- 前端可高亮显示
- 支持quote hash验证（防篡改）
- 真正的"可追溯"

## 风险与缓解

### 风险1: LLM Span Extraction准确性

**描述**: LLM可能无法准确提取evidence spans

**缓解**:
- 使用structured output（Pydantic）
- 添加验证规则（start < end, quote hash匹配）
- 人工review高优先级claims

### 风险2: 性能开销

**描述**: 每个answer都要提取spans，可能增加延迟

**缓解**:
- 异步处理evidence extraction
- 只对高优先级claims提取spans
- 批量处理transitions

### 风险3: 矛盾检测噪音

**描述**: 过度检测矛盾，误报率高

**缓解**:
- 设置严重性阈值
- 只标记MEDIUM/HIGH severity
- 人工确认后才进入CONTRADICTORY
