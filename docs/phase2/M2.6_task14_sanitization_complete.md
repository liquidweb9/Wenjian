## Implementation Summary

### Sanitization Module
- **File**: `app/observability/sanitizer.py` (~200 LOC)
- **Purpose**: Provides utilities to mask PII in text and structured data before logging

### PII Detection & Masking

**Pattern-based detection:**
1. **Email addresses** - Masks username, preserves domain (user@example.com → u***@example.com)
2. **Phone numbers** - Masks all digits (123-456-7890 → ***-***-****)
3. **Chinese ID cards** - Masks all but last 4 digits (110101199001011234 → **************1234)
4. **Credit cards** - Masks all but last 4 digits (1234-5678-9012-3456 → ****-****-****-3456)
5. **Chinese names** - Masks all but first character (张三 → 张*)

**Key-based sanitization:**
- Automatically masks sensitive dictionary keys: `name`, `email`, `phone`, `password`, `token`, `answer_text`, `raw_text`, etc.
- Supports nested dictionaries and lists
- Customizable sensitive key sets

### Core Functions

```python

# Sanitize structured data before logging
```

## Integration Points

### Where to Use Sanitization

**1. When logging user-generated content:**
```python
logger.info("answer_submitted", 
    interview_id=interview_id,
    answer_text=truncate_for_logging(answer_text))  # Sanitized
```

**2. When logging structured data with potential PII:**
```python
logger.info("resume_processed", **safe_log_dict({
    "resume_id": "res1",
    "name": "张三",  # Will be masked
    "email": "user@example.com",  # Will be masked
    "quality": 0.95,  # Not masked
}))
```

**3. When logging error context:**
```python
try:
    process_resume(data)
except Exception as e:
    logger.error("resume_processing_failed", 
        resume_id=data["resume_id"],
        error=str(e),
        # Don't log: data["raw_text"]
    )
```

## Known Limitations

1. **Pattern-based detection limitations:**
   - May not catch all PII variants (e.g., unusual phone formats)
   - May have false positives (e.g., numbers that look like IDs)

2. **Context-dependent PII:**
   - Cannot detect all forms of PII (e.g., addresses, company names)
   - Relies on pattern matching, not semantic understanding

3. **Performance:**
   - Regex operations have overhead (but minimal for typical log volumes)
   - Recommended: use sanitization only when needed, not on every log statement

## Best Practices

### DO:
✅ Use `safe_log_dict()` when logging user-related data  
✅ Truncate long text before logging: `truncate_for_logging(text)`  
✅ Log IDs, counts, and metadata instead of content  
✅ Mask specific fields if you know they contain PII  

### DON'T:
❌ Log `answer_text` or `raw_text` without sanitization  
❌ Log full user objects with `name`, `email`, `phone`  
❌ Log API keys, tokens, or passwords (even hashed)  
❌ Include PII in error messages
