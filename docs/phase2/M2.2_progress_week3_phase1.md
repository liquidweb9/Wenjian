
**功能**:
- 返回claim下所有verification points
- 包含每个VP的evidence count和transition count
- 标记是否有未解决的contradictions
- 按创建时间排序

## 架构设计

### Response Schema Pattern

```python
class VerificationPointResponse:
    """Verification point response schema."""
    def __init__(self, verification_point_id: str, claim_id: str, ...):
        self.verification_point_id = verification_point_id
        self.claim_id = claim_id
        # ... other fields
    
    def to_dict(self) -> dict:
        return {
            "verification_point_id": self.verification_point_id,
            "claim_id": self.claim_id,
            # ... other fields
        }
```

**设计决策**:
- 使用简单的类而非Pydantic models（FastAPI自动序列化dict）
- `to_dict()` 方法提供清晰的JSON转换
- 保持与现有API router的一致性
- 避免过度工程化

### Repository Pattern in API

```python
@router.get("/verification-points/{claim_id}")

    claim_id: str,

):
    evidence_repo = EvidenceRepository(session)
    
    vps = await evidence_repo.get_verification_points_for_claim(claim_id)
    
    # Enrich with counts
    for vp in vps:
        evidence_list = await evidence_repo.get_evidence_for_verification_point(vp.verification_point_id)
        evidence_count = len(evidence_list)
        # ... build response
    
    return {"verification_points": result}
```

**优点**:
- Repository封装数据库访问
- API层只负责HTTP和响应格式
- 易于测试（mock repository）
- 符合Clean Architecture原则

## 关键实现细节

### 1. Evidence Count Aggregation

```python
# Get evidence and transition counts for each VP
for vp in vps:
    # Get evidence count
    evidence_list = await evidence_repo.get_evidence_for_verification_point(
        vp.verification_point_id
    )
    evidence_count = len(evidence_list)
    
    # Get transition count
    transitions = await evidence_repo.get_transitions_for_verification_point(
        vp.verification_point_id
    )
    transition_count = len(transitions)
    
    # Check for contradictions
    contradictions = await evidence_repo.get_contradictions_for_verification_point(
        vp.verification_point_id
    )
    has_contradictions = len(contradictions) > 0
```

**性能考虑**:
- 当前实现：N+1 queries（为每个VP查询counts）
- 可优化：使用SQL COUNT和JOIN减少查询次数
- MVP阶段：简单实现优先，后续优化

### 2. Contradiction Filtering

```python
# Get contradictions
contradictions = await evidence_repo.get_contradictions_for_interview(interview_id)

# Filter by resolution status if provided
if resolution_status:
    contradictions = [
        c for c in contradictions
        if c.resolution_status == resolution_status
    ]
```

**实现选择**:
- 在Python层过滤而非SQL WHERE clause
- 简化repository方法签名
- 便于后续添加更多过滤条件

### 3. 404 Error Handling

```python
# Get verification point
vp = await evidence_repo.get_verification_point(verification_point_id)
if not vp:
    raise HTTPException(status_code=404, detail="Verification point not found")
```

**错误处理策略**:
- 资源不存在返回404
- 空列表返回200（正常但无数据）
- FastAPI自动转换HTTPException为JSON response

## API设计决策记录

### 1. GET Endpoints Only (MVP)

**决策**: Week 3.1只实现GET endpoints，不实现POST/PUT/DELETE

**理由**:
- Evidence数据主要由interview graph自动生成
- 手动修改evidence的场景较少
- GET endpoints足够支持Frontend展示
- 后续按需添加mutation endpoints

### 2. Response Schema使用Simple Classes

**决策**: 使用简单Python类而非Pydantic models作为response schemas

**理由**:
- FastAPI自动序列化dict为JSON
- Pydantic用于request validation，response不需要
- 简单类减少依赖和复杂度
- 与现有API router风格一致

### 3. Repository Pattern而非Direct ORM

**决策**: API通过EvidenceRepository访问数据，而非直接使用SQLAlchemy models

**理由**:
- 封装数据库访问逻辑
- 易于测试（mock repository）
- 保持业务逻辑与数据库实现分离
- 符合Clean Architecture

### 4. Aggregation在Application层

**决策**: Evidence/transition counts在Python代码中计算，而非SQL COUNT

**理由**:
- 简化repository接口
- MVP阶段性能足够（单个claim的VPs通常<10个）
- 后续可优化为SQL aggregation
- 保持代码可读性
